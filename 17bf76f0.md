# GEDSIO Document Analysis System - Comprehensive Prompt Strategy

## Executive Overview

Your system needs to handle **two primary solicitation patterns**:

1. **Multi-Document Solicitations** - Separate PDFs for sections L, M, C, etc.
2. **Single-Document Solicitations** - All sections within one PDF

The challenge is: **identify the pattern, then extract & parse accordingly.**

---

## System Architecture

### Phase 1: Document Classification & Inventory

**Goal:** Understand what you're working with before parsing

```
INPUT: Collection of documents for an opportunity
OUTPUT: 
- Classification: Single-Document or Multi-Document
- Document metadata: File names, sizes, likely sections
- Extraction roadmap: How to proceed
```

### Phase 2: Extraction & Storage

**Goal:** Extract text with context preservation

```
INPUT: Classified documents
OUTPUT:
- Raw text stored in local DB
- Metadata: OpportunityID, DocumentTitle, NoticeID, DocumentType
- Section indicators: Where sections appear (file-level for multi-doc, page-ranges for single-doc)
- Document hashes: For deduplication & update tracking
```

### Phase 3: Parsing & Segmentation

**Goal:** Identify sections and break into analyzable chunks

```
INPUT: Extracted text + classification
OUTPUT:
- Section boundaries: Start/end positions for A, B, C, L, M, etc.
- Subsection identification: Within each section, identify logical divisions
- Content mapping: Text → Section → Subsection structure
- Metadata enrichment: Statement of Work details, evaluation criteria, etc.
```

### Phase 4: Analysis & UI Display

**Goal:** Enable clickable review of structured content

```
INPUT: Parsed sections
OUTPUT:
- Document slideout UI: Click document name → view full content with sections highlighted
- Summary layer: AI-generated section summaries
- Extraction targets: Key data points per section
- Cross-referencing: Link related sections (e.g., "SOW mentions 'security clearance'" → Link to Section H)
```

## MASTER PROMPT FRAMEWORK

### Prompt 1: Document Classification Prompt

**Purpose:** Identify whether solicitation is single or multi-document, extract metadata

```
SYSTEM CONTEXT:
You are analyzing a set of documents for a government contract opportunity. 
Your task is to classify the solicitation structure and provide metadata extraction guidance.

GOVERNMENT SOLICITATION BACKGROUND:
Federal solicitations typically follow FAR guidelines with sections A-M:
- Section A: Information to Offerors
- Section B: Supplies/Services and Price
- Section C: Statement of Work (SOW)
- Section L: Proposal Preparation Instructions
- Section M: Evaluation Criteria
- [Sections D-K: Other administrative/contract details]

DOCUMENT CLASSIFICATION TASK:
Analyze the provided document list and determine:

1. SOLICITATION TYPE:
   - MULTI-DOCUMENT: Separate files for different sections (e.g., "RFP_L_Proposal_Instructions.pdf", "RFP_M_Evaluation.pdf")
   - SINGLE-DOCUMENT: One comprehensive PDF containing all sections
   - HYBRID: Multiple documents but not following standard section breakdown (e.g., "Technical_Requirements.pdf", "Pricing_Instructions.pdf")

2. DOCUMENT INVENTORY:
   For each document, identify:
   - Likely_Section: Which FAR section(s) it contains [A, B, C, D-K, L, M]
   - Document_Type: [Solicitation_Cover, Technical_Requirements, Pricing_Instructions, Evaluation_Criteria, Legal_Clauses, Exhibits, Other]
   - Estimated_Size: [Critical, Standard, Reference]

3. EXTRACTION STRATEGY RECOMMENDATION:
   For multi-document: "Extract each file separately, map to sections, then consolidate"
   For single-document: "Extract all text, apply section detection algorithm, segment by boundaries"
   For hybrid: "Combine multi-document and single-document strategies as needed"

4. POTENTIAL CHALLENGES:
   - Documents that might need special handling
   - Sections that may span multiple files
   - Complex references that need cross-indexing

ANALYSIS FORMAT:
Please provide analysis in JSON format with the following structure:
{
  "classification_type": "MULTI_DOCUMENT | SINGLE_DOCUMENT | HYBRID",
  "opportunity_metadata": {
    "likely_notice_id": "extracted or null",
    "estimated_total_documents": number,
    "total_pages_estimated": number
  },
  "document_inventory": [
    {
      "file_name": "string",
      "likely_sections": ["A", "B", "C", "L", "M"],
      "document_type": "string",
      "size_category": "CRITICAL | STANDARD | REFERENCE",
      "extraction_priority": 1-5,
      "confidence": "HIGH | MEDIUM | LOW",
      "notes": "any special considerations"
    }
  ],
  "extraction_strategy": {
    "approach": "string describing overall strategy",
    "sequence": ["step 1", "step 2", "step 3"],
    "special_handling": ["any documents requiring special attention"]
  },
  "challenges_and_risks": [
    {
      "challenge": "description",
      "mitigation": "how to handle it"
    }
  ]
}

ANALYSIS:
[Provide classification analysis here]
```

### Prompt 2: Single-Document Section Detection Prompt

**Purpose:** When working with a single solicitation PDF, identify section boundaries

```
SYSTEM CONTEXT:
You are analyzing a single government solicitation document containing all sections A-M 
(or a subset thereof). Your task is to identify where each section begins and ends, 
and provide a roadmap for parsing.

STANDARD SOLICITATION STRUCTURE:
Section A: Information to Offerors or Quoters (administrative info, RFQ/RFP cover)
Section B: Supplies or Services and Price/Costs (CLINs, pricing structures)
Section C: Description/Specifications/Statement of Work (SOW, technical requirements)
Section D: Packaging and Marketing (rarely present in new solicitations)
Section E: Inspection and Acceptance (quality/acceptance criteria)
Section F: Deliveries or Performance (delivery schedules, performance requirements)
Section G: Contract Administrative Data (invoicing, payment, POC info)
Section H: Special Contract Requirements (key personnel, compliance, clearances)
Section I: Contract Clauses and General Provisions (FAR clauses, regulatory references)
Section J: Attachments and Exhibits (document index)
Section K: Representations, Certifications, and Other Statements of Offerors (representations)
Section L: Proposal Preparation Instructions (page limits, volumes, formatting)
Section M: Evaluation Criteria (scoring, weights for technical/price/past performance)

SECTION DETECTION TASK:
Analyze the document text and identify:

1. SECTION BOUNDARIES:
   For each section present, provide:
   - Section Letter (A-M)
   - Section Title (exact text or best match)
   - Start Line Number (where section begins)
   - End Line Number (where section ends)
   - Confidence Level (HIGH if explicit heading, MEDIUM if inferred, LOW if uncertain)

2. SUBSECTION MAPPING:
   Within major sections (especially C, L, M), identify subsections:
   - Subsection Name (e.g., "SOW 3.1 Development", "L.2 Page Limits")
   - Subsection Boundaries (start/end line numbers)
   - Relationship to parent section

3. CONTENT CLASSIFICATION BY SUBSECTION:
   For each identified section/subsection, classify the content type:
   - REQUIREMENT: Technical requirement, compliance requirement, deliverable
   - INSTRUCTION: How to prepare proposal, where to submit, format rules
   - EVALUATION: Scoring criteria, weights, pass/fail factors
   - REFERENCE: FAR clauses, cross-references, exhibits
   - ADMINISTRATIVE: Contact info, dates, procurement data
   - LEGAL: Contract terms, liability, compliance clauses

4. CROSS-REFERENCES & DEPENDENCIES:
   - "See Section M for evaluation weights"
   - "As defined in Section C"
   - "Pricing per Section B"
   - These indicate relationships between sections

5. EXTRACTION RECOMMENDATIONS:
   Based on structure identified, recommend extraction approach:
   - Which sections need full-text extraction
   - Which sections need structured parsing (requirements → list)
   - Which sections can be referenced but don't require detailed analysis

ANALYSIS FORMAT:

      "start_line": number,
      "end_line": number,
      "line_count": number,
      "confidence": "HIGH | MEDIUM | LOW",
      "detection_method": "explicit heading | inferred from content | cross-reference"
    }
  ],
  "subsections_detailed": [
    {
      "parent_section": "C",
      "subsection_id": "C.3.1",
      "subsection_title": "Development Phase Requirements",
      "start_line": number,
      "end_line": number,
      "content_classification": "REQUIREMENT | INSTRUCTION | EVALUATION | REFERENCE | ADMINISTRATIVE | LEGAL",
      "key_topics": ["topic1", "topic2"]
    }
  ],
  "cross_references_found": [
    {
      "source_section": "C",
      "source_line": number,
      "reference_text": "quoted text showing cross-reference",
      "target_section": "M",
      "relationship": "constraint | definition | clarification"
    }
  ],
  "extraction_strategy_by_section": {
    "A": {
      "approach": "administrative extract",
      "priority": "LOW",
      "extraction_targets": ["Solicitation Number", "Issuance Date", "Closing Date", "Agency", "POC"]
    },
    "C": {
      "approach": "detailed requirement parsing",
```

### Prompt 3: Requirement Extraction & Parsing Prompt

**Purpose:** Extract specific requirements and content from identified sections

```
SYSTEM CONTEXT:
You are extracting and structuring requirements from government solicitation sections.
Your goal is to identify specific, actionable requirements that a proposal must address.

REQUIREMENT CATEGORIES:
1. FUNCTIONAL REQUIREMENTS: "System must [action]"
2. TECHNICAL REQUIREMENTS: "Must use [technology]", "Performance: [metric]"
3. COMPLIANCE REQUIREMENTS: "Must comply with [regulation]", "Must achieve [certification]"
4. DELIVERABLE REQUIREMENTS: "Deliver [item]", "Provide [documentation]"
5. PERFORMANCE METRICS: "Uptime: 99.9%", "Response time: <2 seconds"
6. SECURITY/CLEARANCE: "TS/SCI clearance required", "CMMC Level 2"
7. PERSONNEL: "Key personnel with [qualification]"
8. SCHEDULING: "Delivery by [date]", "Implementation timeline"

EXTRACTION TASK (For a given section or subsection):

INPUT: Section text (C, H, L, M, etc.) and section metadata

PROCESS:
1. IDENTIFY REQUIREMENT SENTENCES
   - Look for imperative statements: "must", "shall", "should", "will", "required to"
   - Identify conditional requirements: "if [condition], then [requirement]"
   - Extract numbered requirements: "1.", "A.", "(i)" formats
   - Extract bulleted requirements: "• Requirement text"

2. NORMALIZE REQUIREMENT TEXT
   - Remove redundancy: If requirement appears in multiple sections, note all locations
   - Consolidate variants: "Must comply with NIST SP 800-171" and "NIST 800-171 compliant" → single requirement
   - Identify scope: Is this requirement mandatory, optional, or conditional?

3. EXTRACT REQUIREMENT ATTRIBUTES
   For each requirement, extract:
   - Requirement_ID: [SECTION]_[LINE]_[SEQ] (e.g., C_156_3)
   - Requirement_Text: Exact quoted text
   - Requirement_Category: [FUNCTIONAL | TECHNICAL | COMPLIANCE | DELIVERABLE | PERFORMANCE | SECURITY | PERSONNEL | SCHEDULING]
   - Compliance_Level: [MANDATORY | CONDITIONAL | OPTIONAL]
   - Cross_References: Links to other sections where this requirement is mentioned
   - Related_Evaluation_Criteria: If in Section M, which evaluation factor relates to this?
   - Estimated_Complexity: [LOW | MEDIUM | HIGH]

4. BUILD DEPENDENCY GRAPH
   - Identify requirements that depend on other requirements
   - Example: "Key personnel must have TS/SCI clearance" depends on "Personnel identified in proposal"

5. EXTRACT KEY DATES & METRICS
   - Deadline: [date]
   - Delivery Schedule: [timeline]
   - Performance Metrics: [metric definition with value]
   - Staffing Levels: [number] of [role]

OUTPUT FORMAT:
{
  "section": "C",
  "subsection": "C.3 Development Requirements",
  "requirements_extracted": [
    {
      "requirement_id": "C_156_1",
      "requirement_text": "quoted exact text from document",
      "category": "FUNCTIONAL | TECHNICAL | COMPLIANCE | DELIVERABLE | PERFORMANCE | SECURITY | PERSONNEL | SCHEDULING",
      "compliance_level": "MANDATORY | CONDITIONAL | OPTIONAL",
      "condition": "if applicable: what triggers this requirement",
      "key_metrics": {
        "metric_name": "value",
        "unit": "measurement unit"
      },
      "dependencies": ["C_150_1", "H_200_2"],
      "cross_references": {
        "section_L": ["L.5.2"],
        "section_M": ["M.3 Technical Evaluation"]
      },
      "proposal_impact": "How this requirement affects proposal content",
      "verification_method": "How government will verify compliance"
    }
  ],
  "summary_statistics": {
    "total_requirements": number,
    "mandatory_count": number,
    "optional_count": number,
    "critical_dates": [{"date": "YYYY-MM-DD", "description": "Submission deadline"}],
    "key_deliverables": ["list of items to deliver"]
  }
}
```

### Prompt 4: Evaluation Criteria Mapping Prompt

**Purpose:** Extract and map Section M evaluation criteria to Section C requirements

```
SYSTEM CONTEXT:
You are mapping government evaluation criteria (Section M) to solicitation requirements (Section C).
This connection is critical because it shows "how proposals will be scored on meeting requirements."

SECTION M STRUCTURE:
Evaluation criteria typically follow this pattern:
- TECHNICAL: 40-60% weight
  - Approach/Methodology
  - Experience/Past Performance
  - Key Personnel
  - Schedule/Feasibility
- MANAGEMENT: 10-25% weight
  - Organization Structure
  - Qualifications
  - Risk Management
- PAST PERFORMANCE: 10-30% weight
  - Relevant Experience
  - References
  - Similar Projects
- PRICE: 15-40% weight
  - Cost Reasonableness
  - Value for Money

MAPPING TASK:

For each evaluation factor in Section M:
1. Identify which Section C requirements it evaluates
2. Determine the scoring methodology (points, percentages, pass/fail)
3. Identify critical success factors (what must be present to score well)
4. Extract scoring description: How does evaluator determine score?

OUTPUT FORMAT:
{
  "section_m_analysis": {
    "total_evaluation_factors": number,
    "total_weight_percent": number,
    "evaluation_factors": [
      {

}
```

## Database Schema Requirements

```sql
CREATE TABLE opportunities (
  id UUID PRIMARY KEY,
  notice_id VARCHAR(50) UNIQUE,
  title VARCHAR(500),
  agency VARCHAR(200),
  created_at TIMESTAMP,
  classification_type ENUM('SINGLE_DOCUMENT', 'MULTI_DOCUMENT', 'HYBRID'),
  analysis_status ENUM('UPLOADED', 'CLASSIFIED', 'EXTRACTED', 'PARSED', 'ANALYZED')
);

CREATE TABLE documents (
  id UUID PRIMARY KEY,
  opportunity_id UUID REFERENCES opportunities(id),
  filename VARCHAR(300),
  document_type VARCHAR(100),
  file_size INT,
  page_count INT,
  extracted_text TEXT,
  text_hash VARCHAR(64),
  extraction_timestamp TIMESTAMP,
  created_at TIMESTAMP
);

CREATE TABLE sections (
  id UUID PRIMARY KEY,
  document_id UUID REFERENCES documents(id),
  opportunity_id UUID REFERENCES opportunities(id),
  section_letter VARCHAR(1),
  section_title VARCHAR(300),
  start_position INT,
  end_position INT,
  confidence_level ENUM('HIGH', 'MEDIUM', 'LOW'),
  content TEXT
);

CREATE TABLE requirements (
  id UUID PRIMARY KEY,
  section_id UUID REFERENCES sections(id),
  opportunity_id UUID REFERENCES opportunities(id),
  requirement_id VARCHAR(50),
  requirement_text TEXT,
  category VARCHAR(50),
  compliance_level ENUM('MANDATORY', 'CONDITIONAL', 'OPTIONAL'),
  extracted_at TIMESTAMP
);

CREATE TABLE evaluation_mapping (
  id UUID PRIMARY KEY,
  opportunity_id UUID REFERENCES opportunities(id),
  evaluation_factor VARCHAR(300),
  weight_percent INT,
  related_requirement_ids TEXT[],
  created_at TIMESTAMP
);

CREATE TABLE section_summaries (
  id UUID PRIMARY KEY,
  section_id UUID REFERENCES sections(id),
  executive_summary TEXT,
  key_takeaways TEXT[],
  proposal_strategy TEXT,
  red_flags TEXT[],
  opportunities TEXT[],
  generated_at TIMESTAMP
);
```
